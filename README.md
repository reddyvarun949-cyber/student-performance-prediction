# Student At-Risk Prediction

**Methods practised:** descriptive statistics and hypothesis tests — chi-square and t-test (B1 Module 04), exploratory
data analysis (Module 11), classification with pipelines, cross-validation, confusion matrix, precision / recall / F1,
ROC-AUC and threshold choice (Module 08), plus model saving and a simple API.

## Problem statement

A college wants to find students who are likely to **fail the final exam** (score below 40) **early in the term**,
around week 5, so that a mentor can contact them and offer help while there is still time. Given a student's
attendance, study habits, internal test score, previous GPA and background, predict the probability that they are
**at risk**.

Missing a struggling student is much worse than an extra friendly check-in, so the model's alert threshold is chosen on
purpose to **favour recall** (catch most at-risk students), accepting more false alarms.

**Expected result:** a classifier that is clearly better than a "nobody is at risk" baseline, with a threshold chosen
from cross-validation, an honest fairness check by gender, and an API + web form that shows the probability, a risk
level and the main reasons in plain words. (The build run's actual numbers are in `VERIFICATION.md`,
`models/model_info.json` and the executed notebook.)

> **Ethical use:** a flag means *"offer this student support"*. It must never be used to punish, exclude or label a
> student. Mentors and teachers decide; the model only suggests who to talk to first.

## Dataset

Synthetic data for a fictional college, generated by `data/generate_data.py`. Scores follow realistic rules (previous
GPA, the internal test, attendance and study hours matter most; a long commute and poor sleep hurt a little) plus noise.
Gender has **no** effect by design. The target `at_risk` is created from `final_score < 40`, after which `final_score`
is **dropped** because it is only known after the exam (using it would be *data leakage*). See
[data/DATA_DICTIONARY.md](data/DATA_DICTIONARY.md).

What the notebook covers, in order: cleaning (duplicates, impossible values → missing), the leakage demonstration,
EDA (distributions, at-risk rate by group and by attendance band, correlation heatmap), a chi-square test and a Welch
t-test, a stratified split, a preprocessing pipeline, a baseline + logistic regression + random forest
(`class_weight="balanced"`) compared with stratified 5-fold cross-validation, threshold selection for recall, test-set
confusion matrices and ROC curves, logistic coefficients and permutation importance, error analysis of missed students,
a fairness check by gender, new examples with plain-word reasons, saving and reloading, and limitations.

## How to run (three terminals)

**1. Python environment and notebook** (from this project folder):

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate    macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
jupyter notebook notebook/Student_Performance_Prediction.ipynb     # Run All: this creates models/
```

The trained model is already included in `models/`, so you can skip straight to step 2 if you only want the app.

**2. Backend API** (same environment, from this project folder):

```bash
python backend/app.py                 # http://localhost:5000
python -m unittest discover -s backend -p "test_*.py" -v    # optional: run the tests
```

Try it without the frontend:

```bash
curl http://localhost:5000/api/health
curl -X POST http://localhost:5000/api/predict -H "Content-Type: application/json" \
  -d '{"study_hours_per_week":4,"attendance_pct":58,"previous_sem_gpa":5.0,"assignments_submitted_pct":55,"internal_test_score":17,"commute_minutes":75,"sleep_hours":7,"part_time_job":"Yes","family_support":"Low","internet_access":"Yes","extracurricular":"No"}'
```

**3. Frontend** (needs Node.js 18+):

```bash
cd frontend
npm install
npm run dev                           # open http://localhost:5173
```

If the API runs somewhere else, copy `.env.example` to `.env` and change `VITE_API_URL`. If the frontend runs on a
different address, start the backend with `FRONTEND_ORIGIN=http://that-address python backend/app.py`.

## Architecture and request flow

```
 Browser (React form)                  Flask API (backend/app.py)                     models/
 ───────────────────                   ──────────────────────────                     ───────
 page opens ── GET /api/options ────▶  read model_info.json (loaded at start)    ◀── model_info.json
            ◀── labels, ranges, typical values, threshold
 user submits ─ POST /api/predict ──▶  1. parse JSON (400 if not JSON)
   {attendance_pct: 58, ...}           2. validate every field (422 + per-field messages)
                                       3. one-row DataFrame → pipeline.predict_proba ◀── student_risk_model.joblib
                                       4. at_risk = probability ≥ saved threshold
                                       5. risk level (Low / Medium / High)
                                       6. reasons: most important features where the
                                          student is clearly worse than the training median
            ◀── 200 {probability, at_risk, risk_level, threshold, reasons, model, note}
 shows the probability bar, risk badge and reasons, or the error next to the right field
```

- The model is **trained once in the notebook** and loaded **once when the API starts**. Requests only call
  `predict_proba`.
- The saved object is the **whole pipeline**, so missing-value filling, scaling and one-hot encoding are applied exactly
  as during training.
- The **threshold** is not 0.5: it was chosen in the notebook so that cross-validated recall is at least 85%, and it is
  stored in `model_info.json`.
- **Risk levels:** Low = below the threshold; Medium = from the threshold up to `risk_levels.high_from`; High = above.
- **Reasons** are a simple rule of thumb (compare inputs with the training median for the most important features), not
  an exact explanation of the model.

### API reference

| Method | Path | Request | Success response | Errors |
|---|---|---|---|---|
| GET | `/api/health` | — | `{"status": "ok", "model": "...", "threshold": n}` | — |
| GET | `/api/options` | — | `{"numeric_features", "categorical_features", "feature_labels", "categories", "numeric_ranges", "typical_values", "threshold", "risk_levels", "model", "test_recall"}` | — |
| POST | `/api/predict` | JSON with the 11 student fields | `{"probability": n, "at_risk": bool, "risk_level": "Low"\|"Medium"\|"High", "threshold": n, "reasons": [...], "model": "...", "note": "..."}` | 400 body not JSON; 422 `{"error", "fields": {field: message}}` |

Validation rules: all 11 fields required (the API never guesses missing values for a decision about a person); numbers
must lie inside the ranges seen in the cleaned training data (so attendance 120 is rejected); categorical values must be
ones the model has seen. `gender` and `age` are **not** inputs.
